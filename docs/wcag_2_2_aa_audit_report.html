Scope, methodology, and limitations

In scope: the React web app under D:\MySystems\collab-canvas\apps\web: public/authentication pages, dashboard, profile/settings, local and cloud whiteboard shells, sharing/invitation flows, custom dialogs, global CSS, routes, the tldraw integration, generated PNG/PDF board exports, and committed unit/E2E tests.

Method: reviewed TSX, CSS, routes, package metadata, generated application CSS, and all discovered app test files; traced semantic controls, labels, focus handling, status messaging, responsive classes, and export code. Contrast calculations used the WCAG relative-luminance formula against declared theme tokens. The local dev server was started successfully, but the environment exposed no controllable browser session. The audit subagent's initial Vitest attempt was blocked by sandbox permissions; after remediation, the primary environment successfully ran 32 web tests and 7 Worker tests, plus formatting, TypeScript, lint, and production builds. No browser, screen-reader, complete keyboard traversal, zoom/reflow, or automated accessibility scan is asserted.

Status meanings: Pass means the inspected authored code supplies persuasive evidence for the criterion; Fail is a reproducible source-level defect; Not applicable means the feature is absent or the criterion is obsolete; Not tested means source review cannot establish the outcome. “Pass” is not a substitute for the retest activities below.

Third-party boundary: tldraw@5.2.5 supplies the primary drawing UI via apps/web/src/features/whiteboard/whiteboard-canvas.tsx:114-117, 290-293. Its rendered controls and pointer/keyboard behavior were not runtime-tested; related criteria are deliberately not represented as passes for the canvas.

Conformance status and executive summary

Baseline result: not conformant with WCAG 2.2 Level A or AA. Current status: source remediated, manual conformance retest pending. The baseline matrix below is retained as the audit record. Source review and automated regression tests now support closure of F1–F8, but the application must not be represented as conformant until keyboard, screen-reader, zoom/reflow, responsive, contrast-state, and third-party canvas checks pass.

Positive implementation patterns include semantic headings and landmarks, visible labels for normal form fields, decorative Lucide icons generally hidden from assistive technology or paired with text/labels, a global focus indicator for links/buttons/inputs, reduced-motion CSS, a correctly named and focus-managed delete dialog, and live error/status regions in several flows. Those patterns should be extended consistently.

Prioritized findings

F1. Modal focus can escape to obscured page content High

Criteria: 2.1.2 No Keyboard Trap (A), 2.4.3 Focus Order (A), 2.4.11 Focus Not Obscured (Minimum) (AA). Affected users: keyboard-only users, screen-reader users, switch-device users, and users with low vision.

The confirm dialog only focuses Cancel and listens for Escape; it has no Tab containment or focus restoration. The Share dialog has neither focus initialization nor a focus trap. Both expose aria-modal="true", so tabbing to controls behind the visual overlay produces an inconsistent, obscured focus location.

Evidence: apps/web/src/pages/cloud-whiteboard-page.tsx:617-624, 627-660, 856-861, 1035-1041. Contrast: the local delete dialog implements a limited button trap and returns focus at apps/web/src/features/boards/delete-board-dialog.tsx:21-60.

Remediation: use a single reusable dialog primitive. On open, save the trigger, move focus to an appropriate control, keep Tab/Shift+Tab within every enabled focusable descendant, close on Escape, restore focus to the trigger, and make background content inert while open. Give each dialog an explicit name and description.

F2. Share dialog has no accessible name High

Criterion: 4.1.2 Name, Role, Value (A). Affected users: screen-reader and voice-control users.

The dialog has role="dialog" and aria-modal="true", but no aria-labelledby or aria-label; its visible “Share board” heading is not associated with the dialog. Assistive technology may announce only “dialog.”

Evidence: apps/web/src/pages/cloud-whiteboard-page.tsx:856-864.

Remediation: add a stable heading ID and reference it with aria-labelledby; associate the explanatory text through aria-describedby where useful. Verify the announced name in NVDA/Firefox, JAWS/Chrome, and VoiceOver/Safari.

F3. No mechanism skips repeated header/navigation content Medium

Criterion: 2.4.1 Bypass Blocks (A). Affected users: keyboard and screen-reader users who repeatedly navigate between authenticated pages.

No skip link or other bypass control is implemented. The authenticated shell renders repeated header controls before every page outlet.

Evidence: apps/web/src/layouts/app-shell.tsx:13-76; repository search found no skip-link implementation.

Remediation: add the first focusable “Skip to main content” link, target a unique <main id="main-content" tabindex="-1"> in routed pages, and test it at 200% zoom and with a screen reader.

F4. Browser title remains generic across routes Medium

Criterion: 2.4.2 Page Titled (A). Affected users: screen-reader users, browser-tab users, and users switching among boards.

The sole static title is “CollabCanvas”; inspected application source contains no document.title updates. Login, dashboard, settings, profiles, and individual boards therefore share the same title.

Evidence: apps/web/index.html:5-11; apps/web/src/routes/router.tsx:20-56; repository search for document.title returned no matches.

Remediation: set concise route-specific titles (for example, “Boards — CollabCanvas” and “{board title} — CollabCanvas”) using route metadata or a title hook, including loading/error states.

F5. Form-control boundaries do not meet required non-text contrast Medium

Criterion: 1.4.11 Non-text Contrast (AA). Affected users: people with low vision, low contrast sensitivity, or display glare.

The standard control boundary token is #dedfd9 on white (#ffffff), 1.34:1, and the dark equivalent is #363a36 on #202320, 1.37:1. Both are below the 3:1 minimum for visual boundaries used to identify input/select controls. These colors are applied broadly through border border-line.

Evidence: tokens at apps/web/src/index.css:16,19,45,48; representative controls at apps/web/src/pages/login-page.tsx:41-56, apps/web/src/pages/cloud-dashboard-page.tsx:224-265, and apps/web/src/pages/cloud-whiteboard-page.tsx:869-882. Calculated text colors themselves pass: #49655a/#fff 6.38:1, #696e67/#fff 5.21:1, #77998b/#202320 5.08:1, and #a6aaa3/#202320 6.73:1.

Remediation: adopt a control-border token that reaches 3:1 against every adjacent surface in light and dark themes; test default, hover, focus, disabled, error, and selected states with a contrast tool.

F6. Cloud board save/connection updates are not announced Medium

Criterion: 4.1.3 Status Messages (AA). Affected users: screen-reader users collaborating on a board.

Cloud-board status changes such as Saved, Offline, and Connecting are rendered in a plain span with no live-region semantics. The local board counterpart correctly has aria-live="polite", demonstrating an inconsistent implementation.

Evidence: cloud: apps/web/src/pages/cloud-whiteboard-page.tsx:368-375; local: apps/web/src/pages/whiteboard-page.tsx:158-169.

Remediation: make the cloud status a stable, concise polite status region (or use role="status"), avoid duplicate announcements, and verify connection/save/error announcements with screen readers.

F7. Board exports are raster-only and the generated PDF is untagged Medium

Criteria: 1.1.1 Non-text Content (A), 1.3.1 Info and Relationships (A). Affected users: people who cannot perceive a board image and people using screen readers or reflow/structure tools on exported PDFs.

The export path converts the board to a PNG, then embeds that PNG as the only PDF page content. It supplies no alternative text, semantic structure, or tagged-PDF metadata. Exported boards may contain arbitrary user content, but the application currently provides no accessibility-preserving or text-alternative export path.

Evidence: apps/web/src/pages/cloud-whiteboard-page.tsx:221-255.

Remediation: provide an accessible textual/structured companion export (such as board object list, notes, and reading order) and clearly label the PNG/PDF as visual exports. If accessible PDF is promised, generate tagged PDF with meaningful document structure and alternatives; test the resulting file with Acrobat Accessibility Checker and a screen reader.

F8. Global focus styling does not explicitly cover every custom control type Low

Criterion: 2.4.7 Focus Visible (AA) — conservative source-review failure for the authored focus system; validate in browsers during retest. Affected users: keyboard users.

The global rule targets only button, input, and anchor elements. Selects and some summary controls rely on browser defaults, while the interface uses custom border/background styling. A browser-default outline may remain, but that is not an explicit, cross-browser focus treatment for the application’s control set.

Evidence: apps/web/src/index.css:61-71; selects at apps/web/src/pages/cloud-dashboard-page.tsx:224-251; summaries at apps/web/src/layouts/app-shell.tsx:46-52 and apps/web/src/pages/cloud-whiteboard-page.tsx:399-429.

Remediation: define a shared :focus-visible treatment for button, a, input, select, summary, [tabindex] and custom tldraw controls; test focus visibility against each theme and background.

Testing evidence and retest checklist

Evidence reviewed

  • Routes and layouts: apps/web/src/routes/router.tsx, apps/web/src/layouts/auth-layout.tsx, and apps/web/src/layouts/app-shell.tsx.
  • All page TSX files under apps/web/src/pages; shared board, collaboration, whiteboard, and auth components under apps/web/src/features; apps/web/src/index.css; apps/web/index.html.
  • Automated remediation verification: 32 web tests pass across 11 files, including new dialog keyboard/semantics, route-title, and accessible-export tests; all 7 Worker tests pass. Formatting, strict TypeScript, ESLint, the Worker dry-run build, and the web production build pass.
  • apps/web/e2e/collaboration.spec.ts remains environment-gated and does not provide accessibility assertions. No axe or pa11y integration is configured. Runtime browser control and assistive-technology sessions were unavailable, so automated success does not establish conformance.

Required retest sequence

  1. Run the repaired app in Chrome, Firefox, Safari, and Edge. Complete every route in light/dark themes at 200% zoom, 400% zoom/320 CSS px, and text-spacing overrides.
  2. Keyboard-test all routes: Tab/Shift+Tab, Enter, Space, Escape, dialogs, details menus, dashboard cards, file picker, sharing, invitations, export, and whiteboard toolbar/canvas. Confirm dialogs contain focus and restore it to their trigger.
  3. Screen-reader test NVDA + Firefox, JAWS + Chrome, and VoiceOver + Safari. Verify page titles, skip link, dialog name/description, save/connection/presence/error announcements, input labels, and tldraw interactions.
  4. Run an automated scanner (axe-core) on unauthenticated pages, authenticated dashboard/profile/settings, empty/populated board, Share dialog, confirmation dialogs, and error states. Manually review every result; scanners do not prove conformance.
  5. Measure all text/non-text/focus contrasts in both themes, including tldraw controls and disabled/error states. Validate target sizes and non-drag alternatives on touch and keyboard.
  6. Inspect generated visual PNG/PDF exports and the semantic HTML companion. Verify that all available board text appears in spatial reading order and that the HTML is usable with a screen reader. Continue to describe PDF as visual unless a separately tested tagged-PDF implementation is introduced.
  7. Run the gated E2E suite with configured accounts and add an axe-based browser suite for titles, skip links, dialog semantics/focus restoration, live status, both themes, and representative populated boards.
