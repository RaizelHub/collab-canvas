Laws of UX analysis

Dashboard, authentication, whiteboard, collaboration, sharing, recovery, responsive behavior, and product copy in the implemented React application.

Executive summary

Overall assessment

3.3 / 5

CollabCanvas has a calm, consistent visual system and a good foundation of direct manipulation: familiar forms, explicit labels, stable board cards, loading/error states, recovery messaging, and confirmation for destructive board deletion. The cloud whiteboard also exposes useful collaboration, export, snapshot, and presence feedback.

The largest experience risks are not visual polish. They are mismatches between product promises and reachable behavior: the router blocks the advertised local mode without a Supabase configuration; links marketed as “Public” or “Link” still require sign-in; important whiteboard status and collaboration cues disappear at compact widths; and two custom dialogs lack complete modal keyboard containment.

First changes to make

  1. Decide whether local mode and public/link sharing are real supported modes, then align routing and copy.
  2. Use one accessible modal primitive with focus trap, Escape, focus restoration, and an explicit close control.
  3. Keep a compact, always-visible save/connection and collaborator indicator on small screens.
  4. Add pending/success/failure feedback around destructive and clipboard actions.
Evidence boundary This audit inspected the actual TypeScript/TSX/CSS/routes and existing tests. The in-app browser connection reported “No browser is available,” so no live UI, authenticated session, network timing, screen-reader, or real-device observation is claimed. Statements labelled source-verified are grounded in the linked local code; runtime assertions are deliberately deferred to the validation plan.

Evidence-backed findings

P1 — high impactMedium effortJakob · Tesler · error prevention

Advertised local mode is blocked by the route guard

Source-verified. The dashboard and local whiteboard implement a “Local foundation mode” / “Local mode” experience, but all dashboard and board routes sit inside ProtectedRoute. When Supabase is absent, that guard renders only a setup-required screen. A person following the local-mode copy cannot reach the local dashboard or canvas through the real router.

Why it matters: This turns a low-complexity fallback into an infrastructure prerequisite, eroding trust at the first-use peak. Either permit intended local routes without authentication, or remove/replace the local-mode promise and make the setup requirement clear before users invest effort.

Evidence: router.tsx:35–50; protected-route.tsx:9–23; dashboard-page.tsx:145–155; local-mode-badge.tsx:3–9.

P1 — high impactMedium effortJakob · Hick · error prevention

Sharing vocabulary implies access that the implemented route does not grant

Source-verified. The sharing selector offers “Link — view only,” “Link — can edit,” and “Public — view only.” Yet the share route is protected, unauthenticated visitors are redirected to sign-in, and the share page requests a session token before opening. “Public” therefore does not behave as most people expect unless its meaning is explicitly “all signed-in users permitted by server policy.”

Recommendation: Make the labels match the enforced model (for example, “Anyone with an account and this link”), or intentionally support anonymous access and test its security model. Add one-sentence consequence text beside each access choice and require confirmation when broadening exposure or granting edit access.

Evidence: cloud-whiteboard-page.tsx:878–882; router.tsx:47–50; protected-route.tsx:36–44; share-link-page.tsx:30–45.

P1 — high impactMedium effortAccessibility · common region · control

Custom Share and clear/restore dialogs do not provide a complete modal interaction

Source-verified. Both dialogs use role="dialog" and aria-modal="true". The confirmation dialog initially focuses Cancel and supports Escape, but neither it nor Share traps Tab focus or restores the invoking focus when closed; Share also has no Escape handler or explicit close button. By contrast, Delete board does trap Tab and restore focus, proving a usable implementation pattern already exists in the codebase.

Recommendation: Standardize on a single dialog component or native <dialog> pattern: labelled dialog, first meaningful focus, Tab/Shift+Tab containment, Escape unless unsafe, visible close, background inertness, and focus return. Test keyboard-only flow with each dialog.

Evidence: cloud-whiteboard-page.tsx:606–661; cloud-whiteboard-page.tsx:856–1044; comparison: delete-board-dialog.tsx:21–60.

P2 — medium impactLow–medium effortFeedback · Doherty · responsive UX

Compact whiteboard removes all source-visible collaboration and save context

Source-verified. At smaller breakpoints, the cloud header hides connection/save status below md, the collaborator menu below sm, and local-mode identity below lg. The remaining mobile header leaves users with actions but less evidence that work is connected, saved, local, or shared. The app does preserve the board title and Back action, which is a useful foundation.

Recommendation: Use compact icons/badges with accessible names rather than removing the status wholesale: e.g., a colored connection dot with “Offline—changes may not sync,” an avatar count, and a one-time local-mode badge. Verify at 320, 375, 390, 768, and landscape.

Evidence: cloud-whiteboard-page.tsx:338–398; collaborator-menu.tsx:15–30; whiteboard-page.tsx:158–172; responsive dashboard grid: cloud-dashboard-page.tsx:277–294.

P2 — medium impactLow effortError prevention · peak-end · feedback

Cloud deletion closes before its outcome is visible and has no progress/undo state

Source-verified. Confirming deletion immediately clears the dialog state, then performs the asynchronous cleanup. Failure later appears in a dashboard alert with Retry, but the affordance has already vanished and the button is not disabled during the request. The permanent-delete warning is good, but the action’s ending is less reassuring than it could be.

Recommendation: Keep the dialog open while deleting, replace the action with “Deleting…”, prevent duplicate submission, then close on success and announce “Board deleted.” Consider a short undo only if the backend can support recoverability; otherwise keep the permanent consequence unmistakable.

Evidence: cloud-dashboard-page.tsx:100–129; delete-board-dialog.tsx:73–96.

P2 — medium impactLow effortJakob · navigation · serial position

Recent/shared routes exist but are not represented in the application shell

Source-verified. The router declares /boards/recent and /boards/shared, and the cloud dashboard filters based on those paths. The shell only offers “Dashboard”; there is no source-visible link, tab, or navigation control for Recent versus Shared. Users can filter by role, but the route-level organization cannot be discovered through normal navigation.

Recommendation: Choose one mental model: add visible tabs/segmented navigation for All, Recent, Shared; or remove the hidden routes and state the card filters in the dashboard. Retain the current search, role, and sort controls as secondary refinements.

Evidence: router.tsx:40–44; app-shell.tsx:25–31; cloud-dashboard-page.tsx:167–185.

P2 — medium impactLow effortFeedback · accessibility · recovery

Several outcomes are silent or visually inaccessible

Source-verified. Copying share/invitation links directly calls the clipboard API without success/failure feedback. Local whiteboard title errors are placed in a screen-reader-only alert, so a sighted user receives no visible explanation after an invalid blur/save. Reset-password submission also exposes no in-progress state, unlike sign-in and registration.

Recommendation: Announce “Link copied” (and copy failure), show title errors adjacent to the field with aria-describedby, and add a disabled busy state to password-reset submission. These small endings improve perceived reliability disproportionately.

Evidence: cloud-whiteboard-page.tsx:895–902 and :975–982; whiteboard-page.tsx:151–155; password-pages.tsx:11–51.

P2 — medium impactLow effortFitts · accessibility

Interactive target and focus treatment is inconsistent at the compact end

Source-verified. Primary form controls are 40px high and Create is 36px, while several board/header actions are 32px. The global explicit keyboard focus selector covers buttons, inputs, and links, but not summary or select; some summaries add local focus styling and others do not. This is not a claim that they are unusable—the browser may supply an outline—but it is not guaranteed by the product stylesheet.

Recommendation: Set a 40–44px minimum target for touch-primary icon actions and a shared :focus-visible rule for button, input, select, summary, and links. Preserve compact desktop density only where pointer use is known.

Evidence: index.css:61–71; board-card.tsx:114–150; app-shell.tsx:46–52; collaborator-menu.tsx:15–16.

P3 — opportunityMedium effortGoal gradient · Miller · aesthetic-usability

New-board momentum can be made more intentional

Source-verified to the navigation behavior; onboarding absence is limited to application-owned UI. Creating a board takes the user straight to an “Untitled board” canvas, which is fast and respects direct manipulation. No application-level starter prompt, first-success check, or visible next-step sequence is rendered before handing control to the third-party canvas UI. Whether tldraw itself supplies onboarding must be verified at runtime.

Recommendation: On a fresh board, offer a dismissible, one-task-at-a-time starter strip: “Name board → add a note → share when ready.” Do not cover the canvas toolbar; remove the cue after the first object or store dismissal.

Evidence: cloud-dashboard-page.tsx:61–75; supabase-board-repository.ts:188–199; cloud-whiteboard-page.tsx:517–572.

Flow-by-flow analysis

1. Sign in, register, and reset password

  1. Recognition: Standard labels, email/password types, autocomplete and inline navigation align with Jakob’s Law.
  2. Feedback: Sign-in/registration disable and change labels while submitting; alerts show provider errors.
  3. Gap: registration has no explanatory configured-state message even though its CTA is disabled, while login does; reset password has no busy guard.

login-page.tsx:33–72; register-page.tsx:86–92; password-pages.tsx:11–51.

2. Dashboard, board discovery, and board lifecycle

  1. Scan: one CTA, search, and responsive card grid support visual chunking and progressive disclosure.
  2. Manage: inline rename accepts Escape and reports errors; deletion uses the strongest modal behavior in the app.
  3. Gap: Cloud Recent/Shared route distinction is not navigable; cloud deletion ends the confirmation before request completion.

cloud-dashboard-page.tsx:187–321; board-card.tsx:34–154.

3. Create and work on a whiteboard

  1. Momentum: Create produces an Untitled board and navigates directly to its canvas—good goal-gradient support.
  2. Status: Cloud mode computes Connecting/Offline/Saved state and announces changing collaborator presence; local mode announces saved changes.
  3. Gap: source-visible state is intentionally hidden at narrow breakpoints. Local invalid-title feedback is not visually presented.

cloud-whiteboard-page.tsx:165–190, 367–376, 500–571; whiteboard-page.tsx:80–119, 151–169.

4. Share, invite, and manage access

  1. Choices: Access level, invitee email, and role are explicit, and the member list permits role changes/removal.
  2. Feedback: status copy announces saving, invitation creation, expiration and member updates.
  3. Gap: immediate exposure changes and semantics of “Public/Link” require clarification; copied links provide no confirmation; the dialog keyboard model is incomplete.

cloud-whiteboard-page.tsx:718–818, 856–1044.

5. Failure, recovery, and exit

  1. Recovery: protected routing restores a session or preserves the intended redirect; unavailable boards return users to the dashboard.
  2. Resilience: canvas and app error boundaries provide human-readable refresh instructions; local metadata corruption has a reset path.
  3. Gap: recovering from failed destructive or sharing operations should leave the initiating context intact and explain the next safe action.

protected-route.tsx:25–47; error-boundary.tsx:25–44.

Principles not independently applicable or not verifiable from source alone

  • Von Restorff effect: no important isolated/exceptional item is a repeated decision point in the reviewed application-owned UI; applying it would be speculative.
  • Parkinson’s Law / timeboxing: the product has no source-visible deadlines, estimates, task timers, or paced multi-step workflow.
  • Law of Uniform Connectedness: supported incidentally by panels/borders, but it does not create a distinct finding beyond the Gestalt review.
  • Canvas-tool palette, drawing latency, and viewer editability: tldraw is an embedded dependency. The app passes a store to <Tldraw>, but source review alone cannot establish its rendered toolbar, gesture behavior, frame rate, or whether server authorization makes viewer controls read-only. Verify these live before making a claim.
  • Doherty’s <400 ms threshold: no performance measurements, RUM telemetry, or a connected runtime was available. Existing loading feedback is assessed; actual response timing is not.

Validation plan

  1. Route/copy decision test: In a clean browser with no Supabase environment, attempt /dashboard and /board/:id. Confirm the chosen product policy (local access or setup gate) matches every label. With a logged-out session, open each share mode and record expected/actual access.
  2. Keyboard modal test: For Delete, Share, Clear, and Restore: open using keyboard; ensure focus enters the dialog, Tab/Shift+Tab never escapes, Escape behavior is intentional, close returns focus to the invoking control, and screen-reader title/description are announced.
  3. Responsive task test: At 320×568, 375×667, 390×844, 768px, and desktop, have 5 participants complete: create a board, determine whether it is saved/online, find collaborators, share view-only, and return to the dashboard. Track failures, hesitation, and horizontal overflow.
  4. Destructive-state test: Simulate slow and failed cloud deletion, visibility update, clipboard denial, reset email request, asset upload and snapshot restore. Confirm button busy state, outcome feedback, retry location, and retained context.
  5. Accessibility test: Run automated checks (axe or equivalent) and manual keyboard/VoiceOver/NVDA testing. Specifically inspect contrast in both themes, summary/select focus, live-region announcement frequency, role labels, zoom to 200%, and reduced-motion behavior.
  6. Outcome metrics: Compare before/after task success, time-to-first-board, share-permission comprehension, accidental permission-change rate, repeat-click rate, and mobile confidence rating. Set a response-time budget and collect real interaction timing before claiming Doherty-threshold compliance.
